# 耐萌 · 商务动作入口

粘贴微信内容 → AI 识别 → 商务确认 → 一条合作记录入库。

零第三方依赖，只用 Node 内置模块。不装 npm 包，不用构建。

---

## 快速开始

```bash
cd naimeng-intake
npm run dev        # node --watch，改代码自动重启
```

打开 `http://localhost:5173`。第一次进来会让你**设置团队口令**并填自己的姓名和角色，之后同事各自打开、输口令、从名单里选自己就能用。登录状态保留 30 天。

**不配模型也能跑** —— 此时用内置的本地模拟识别，够把流程走通，准确率明显低于真实模型。
配好模型后一定要点「测试连接」确认，**保存成功不等于配置生效**。

部署到办公室 Mac mini 供局域网访问，见 [`docs/DEPLOY-macmini.md`](docs/DEPLOY-macmini.md)。

> 改了代码但页面没变化？多半是旧进程还占着端口。`npm run dev` 报 `EADDRINUSE` 就是这个原因，先 `taskkill /F /IM node.exe`（Windows）再起。

## 核心概念：一次合作

**叙事主体是「一次合作」，不是「一个达人」。**

```
达人 creator          稳定身份 + 归属人 + 默认收件信息
  └ 抖音账号 account   抖音号 / UID / 合作码（合作码长期不变，第二次合作自动带出）

合作 collaboration     一次合作 = 一个收件地址 + 一笔费用
  ├ 产品行 ×N          可以寄多个产品，各自数量
  ├ 履约项 ×N          每个参与账号一条：拍摄进度 + 视频口令
  └ 包裹 ×N            一次合作可以拆成多个快递单
```

同一个达人再次合作，就是**新增一条合作记录**，账号和合作码复用，不新建达人。

**三种合作类型**：

| 类型 | 寄实物 | 产品 / 收件信息 | 初始状态 |
|---|---|---|---|
| 寄样合作 | 是 | 提交寄样时必填 | 待寄样 |
| 不寄样合作 | 否 | 不需要（界面折叠） | 进行中 |
| 直播定向 | 否 | 不需要（界面折叠） | 进行中 |

后两者都不寄实物 —— 前者是达人手里已有货或纯投流，后者是给直播间开定向。
对系统的意义完全一样，所以判断集中在 `rules.needsSample(type)` 一个函数里，
而不是散在各处比较字符串。再加一种不寄样的类型只改那一处。

**未知类型按寄样处理。** 反过来的话，一个拼错的字符串就能绕过收件信息的
必填校验，而表现是东西寄不出去。宁可多问一句。

**为什么合作要独立于达人**：换地址、换商品、不同账号组合，只有合作级快照能记对历史。收件地址存两份 —— 达人身上那份是录入时的默认值（地址基本不变，重填很烦），合作上那份是这次实际用的快照。

**为什么履约项是账号级**：一次合作可以挂多个抖音号，但拍摄进度和视频链接必须跟具体账号对应。两个号一起寄样，可能一个已发布另一个还在拍。这正是 Excel 表达不了、系统天然能做到的地方。

## 状态由动作驱动

**界面上没有让人手选状态的下拉框。** 状态一旦能手选，就会退化成 Excel —— 填的人凭印象改，越用越不准。

| 层 | 状态 | 由什么触发 |
|---|---|---|
| 合作 | 待寄样 | 提交寄样合作时 |
| | 进行中 | 提交**不寄样**的合作时（跳过整个寄样阶段） |
| | 已寄样 | **回填快递单号时** |
| | 已完成 | 所有需出片账号都已回传时 |
| | 已终止 | 手动（达人失联/放弃） |
| 履约项 | 待拍摄 | 合作创建时 |
| | 已催拍 | 记录回访结果时 |
| | 已发布 | **粘贴视频口令时** |
| | 本次不出片 | 手动 |

「已告知达人」是合作上的标记位，不是状态 —— 它和寄样状态正交。

不寄样的合作不落成「待寄样」，是因为那样表里会一直挂着一个永远不会被寄的东西：
筛选「待寄样」的人以为有活要干，点进去才发现根本不需要寄。

## 两个入口

界面按「一次合作的一生」组织，不按系统功能分区。

早先版本分成「录入 / 我的待办 / 记录查询」三个 tab —— 录入是动作、待办是提醒、
记录查询是数据库，三个不同层级的东西被摆成了同级。而商务的一天只有一种起点：
微信里来了一条消息，处理它。

### 1. 工作台

顶部一条粘贴框（聚焦才展开），下面是**「需要处理」**。

识别队列和待办合并在这里 —— 它们本就是同一件事：等着你动手的东西。
拆成两处的后果是，在待办里看到「该催拍了」，想看详情还得切页面重搜一遍。

粘贴时实时显示「识别为：建档 / 视频回传」和判断依据，判错了右边下拉手动改。

| 输入类型 | 判定依据 | 处理 |
|---|---|---|
| 达人资料 | 含 UID / 合作码 / 手机号 | LLM 识别，**进后台队列**，输入框立刻清空可继续粘 |
| 视频口令 | 含 `v.douyin.com` + 【昵称】，且无上述三者 | **本地正则，0 延迟不调模型**，直接进确认页 |
| 发货截图 | 上传或 Ctrl+V 粘贴图片 | 视觉模型识别，**1→N**，进批量回填页 |

**关键保险**：只要出现 UID / 合作码 / 手机号，一律判为建档。因为达人资料里常夹带抖音**主页口令**（也含 `v.douyin.com` 链接），只看链接会误判。

「需要处理」每条只显示四样：达人名、状态、一句摘要、操作。细节都留到确认抽屉里说。

| 来源 | 出现在清单里的形态 |
|---|---|
| 识别中的任务 | 「识别中」+ 可取消，**不阻塞你粘下一条** |
| 识别完待确认 | 「识别完成」+ 待补充项数 + 去确认 |
| 该告知达人 | 复制物流并标记已告知（**一步**）|
| 该回访了 | 复制话术 / 记录回访 |
| 等快递单号 | 回填快递 |
| 草稿、识别失败 | 继续录入 / 重试 |

### 1.5 发货截图批量回填

仓库把速店通/菜鸟的发货列表截图发到微信，商务直接 Ctrl+V 粘进来（或点上传区选图）。识别完在队列点「去回填」，进批量匹配页：高置信默认勾选，低置信和没匹配上的手动选，「确认回填」一次过。

**匹配为什么只能是模糊的**：截图里手机号和地址门牌都是打码的（`18*****47`、`南翔镇依仁路88弄**17号2501室`），做不了精确比对。所以：

| 信号 | 权重 | 说明 |
|---|---|---|
| 收件人姓名 | 完全一致 +50 / 包含 +35 | 有脏数据，如「于小姐联系方式」被整串当成姓名 |
| 手机首尾 | +25 / **对不上 −30** | 只剩前 2 位和后 2 位，用于消歧 |
| 地址可见片段 | 按命中比例 +0~30 | 用 `*` 切开逐段比对，**不猜被遮住的内容** |
| 商品名 | +5 | 仅佐证 —— 截图是速店通的 SKU 名，跟系统预置产品名大概率对不上 |

≥60 分且无歧义 → 高置信；≥40 分 → 低置信需确认；前两名分差 <10 分标 `ambiguous`，**不敢自动选**。已完成/已终止的合作不参与匹配，单号已存在的直接标「已回填过」。

一次发货拆多个包裹时同一收件人会出现多行，提示词里明确要求**逐行提取不合并**。

待办由状态推导，**不存表**，做完自动消失：

| 待办 | 触发 |
|---|---|
| 告知物流 | 有单号但未告知。**复制即视为已告知** —— 工作台和合作详情是同一套做法 |
| 等快递单号 | 已提交寄样但无包裹，超 3 天标逾期 |
| 回访催拍 | 建档满 N 天仍有账号未发布 |
| 补全信息 | 合作没有产品行，仓库无法备货 |
| 草稿未完成 / 识别失败 | |

回访**从建档日期起算**（团队现行做法），不依赖发货时间。语义是回访不只是催拍：先问收没收到，收到了再催。

#### 发货截图会留档

识别完之后**原图保留**，确认页右栏就是它，点一下全屏放大。
快递单号在截图里往往很小，缩略图上根本认不出 —— 不能放大的预览等于没有预览。

回填之后仍然能查：合作详情 → 寄样信息，截图识别来的那条快递下面有
「点击查看原图」。手工填的没有图，也就不放这个入口。

**图存文件不存库。** 一张 base64 之后 0.5～3 MB，而启动时会把整个
`naimeng.db` 备份并保留 7 份 —— 图片进库等于这些体积乘以 7，
而备份的价值在达人资料和合作记录，不在几个月前的一张快递截图。
所以落到 `data/shots/`，库里只存一个 id，超过 1000 张从最老的删起。

**原图走接口不放静态目录** —— 静态目录意味着同网段谁都能按 id 猜着看。
id 用白名单校验（必须长成 `sh-xxx-yyy`）而不是「过滤掉 `..`」：
过滤是黑名单思路，且对不含 `..` 的名字完全放行，目录里任何文件都能被读出去。

图被清理之后前端显示「原图已清理」而不是一个破图框。

### 2. 合作记录

八列，每一列回答一个具体问题：

| 列 | 回答什么 |
|---|---|
| 达人 / 账号 | 是谁。**多账号一行一个**，不拼在一格里 —— 矩阵号一多就分不清哪个昵称对应哪个号 |
| 状态 | 到哪一步了 |
| 寄样 | 寄什么、几件 |
| 快递 | 发没发、单号多少 |
| 视频 | 几个号发布了 / 一共几个要出片 |
| 飞书同步 | 推过去没有 |
| 建档 / 更新 | 什么时候建的、最后动过是什么时候 |

> **「快递」那一列只说「待发货 / 已发货」。**
> 系统里没有物流数据源 —— 快递公司和单号都是人填的，包裹到哪了没人知道。
> 写「运输中」「已签收」就是在编，而且没人能发现它是编的。
> 真要轨迹得接快递查询 API，那是另一件事。有测试专门禁掉这几个词。

**视频进度按「要出片的账号」算分母**，标了「本次不出片」的号不计入 ——
算进去的话这条永远凑不齐，看起来像一直没做完。

#### 合作详情：五张卡片

标题是 `建档日期 · 达人名称` 加状态胶囊 —— 同一个达人可能有很多次合作，
日期是唯一能一眼分开它们的东西。

| 卡片 | 内容 | 能做什么 |
|---|---|---|
| 达人档案 | 每个抖音账号的昵称 / 抖音号 / UID / 合作码 | 每条点一下复制 |
| 寄样信息 | 产品、费用、收件信息、快递 | 没单号→回填；有单号→复制整段物流信息 |
| 视频信息 | 每个要出片账号的链接和口令 | 没链接→填写或标记「本次不出片」；有链接→复制整段 |
| 商务信息 | 归属商务、合作类型、带货方式 | 转交归属 |
| 系统信息 | 合作ID、建档 / 更新 / 告知时间、飞书同步 | 手动同步 |

**每条信息整行都是复制热区** —— 手机号和长地址用鼠标划选很容易划错。
口令**复制的是原文而不是显示用的截断版**：抖音跳转和千川加载都依赖它逐字节相同。

**底部只放终止和删除。** 日常操作（回填、复制、催拍）放在各自的卡片里 ——
混进底部，「这一排都是危险动作」这条规律就失效了。

**删除是不可逆的**，所以：只有归属商务能删（非归属人看到的是禁用按钮而不是
藏起来的按钮 —— 藏起来会让人以为没这功能）；两道确认，第二道要**手打达人名字**。
一次「确定」拦不住顺手点。

删除会连带删掉产品行、履约项、包裹，以及飞书里对应的行。
**达人档案保留**（他可能还有别的合作），**录入日志保留**
（那是调优提示词的语料，和这次合作在不在没有关系）。

#### 两个刻意合并掉的动作

**「标记已告知达人」没有独立按钮** —— 复制完整物流信息即视为已告知，
**工作台的待办卡片和合作详情用的是同一套做法**。

那个按钮存在的唯一目的就是把物流信息粘给达人，复制完还要再点一下
「我复制了」，是让人做一件系统已经知道的事。
代价是复制完又没发出去时系统会以为告知过了；相比「每次都多点一下、
而且经常忘」，这个代价更小。

> 这两处曾经不一致：工作台两步、详情一步。同一个动作两种语义，
> 用哪边的人都会觉得另一边不对劲 —— 有测试守着它们不再分叉。

**「本次不出片」和填视频链接在同一个弹窗里** —— 打开它的时机是一样的
（商务问完达人有了结果），结果无非这两种。分成两个入口会让人先想
「我该点哪个」。勾了不出片，链接框会变灰 —— 留一个能填但会被忽略的框是骗人。

弹窗还会在粘进完整口令时自动抠出链接：达人发来的常常是一整段口令，
让人自己从里面找链接是多余的一步。

#### 时间线可以点开原文

建档那个节点点一下，能看到**原文、模型输出、以及人工改了哪些字段**。
排查「这个字段怎么是错的」时，这是唯一能回答的地方。

只有建档节点可点 —— 快递和视频只有来源标记，够不上「识别记录」。
**点了什么都不弹，比不能点更让人困惑。**

原文里有达人的真实姓名、手机号、地址，所以这个接口和其他按 id 直取的
接口一样拦归属。

## 确认抽屉 —— 一种容器，四类内容

建档、视频回传、发货截图、合作详情**共用同一个抽屉**。
左边是系统的判断，右边恒为证据 —— 商务只要学一次「往右看」。

早先版本里建档是覆盖层、视频是独立页、快递单又是另一个独立页，
同样一件「AI 识别完了你确认一下」的事，要学三套界面。

| 内容 | 右栏是什么 |
|---|---|
| 建档 / 新合作 | 原文，点字段自动定位高亮 |
| 视频回传 | 逐字节保存的口令原文 |
| 发货截图 | 截图本身 |
| 合作详情 | 这次合作的产品、收件、快递、归属 |

**没有完成页。** 提交后抽屉关闭 + 一条 toast，焦点回到粘贴框。
队列本来就是异步的，完成页会打断「提交完立刻粘下一条」的节奏，
而它唯一提供的价值 toast 就够。

合作详情用**时间线**呈现：建档 → 已寄样 → 已告知 → 等待出片 → 已完成。
每一格都对应一个真实发生过的动作，没有一格是人手选的 ——
这把「状态由动作驱动」这条规则可视化了，顺便让「为什么这条是已寄样」不用解释。

### 建档确认的细节

- 识别完光标自动落在第一个空字段，`Alt+N` 在待补充 / 需核对字段间跳转
- 点任意字段，右侧原文自动定位高亮
- 资料分几条消息发来？右侧可继续粘贴新片段「合并识别」
- 命中已有达人时，主按钮是「**在该达人上发起新合作**」，不新建达人
- 「仅建档，暂不寄样」和「确认并提交寄样」分开 —— 只想先建档就不用凑齐产品和地址

### 校验按动作分级

**必填不挂在记录上，挂在动作上** —— 每个字段阻断的是真正需要它的那一步。

| 动作 | 硬阻断 |
|---|---|
| 存草稿 | 无 |
| 仅建档 | 至少一个账号有抖音号或 UID |
| 提交寄样 | 收件人 + 手机 + 地址 + 至少一个产品行 |

依据：27 条真实样本里 **4 条完全没有合作码**（其中一条一次挂 6 个账号），3 条只有 UID 没有抖音号。若把三者做成硬性必填，这些资料一条都录不进去，商务只能绕过系统。但合作码不该拦寄样 —— 发货不需要它，它该拦的是投流。

## 视频口令必须完整保存

**口令是功能载体，不是噪声。**

```
0.58 复制打开抖音，看看【某某某的作品】…… https://v.douyin.com/XXXX/ :9pm KWM:/ 01/13 z@T.Lw
```

复制**整段**打开抖音会自动跳转到视频；投流时粘贴整段，千川会自动加载素材。只存清理过的 URL，运营在千川里就加载不出来，还得回头找商务要原文 —— 视频交接就落空了。

所以 `shareToken` 逐字节保存：不 trim、不去表情、不清理尾串。尾部那串看着像垃圾的字符正是抖音识别口令的一部分。

界面上的可点击链接只是预览，**交接一律用「复制口令」按钮**。合作详情里每个已发布的履约项都有这个按钮。

昵称从【】里提取，用来自动匹配这条视频属于哪个账号的哪次合作。匹配不上（达人改过昵称）会提示手动选，不会静默失败。

## 设置

右上角「设置」。**菜单按角色裁剪** —— 仓库和运营看不到模型与 API Key 设置。

**用户设置** —— 姓名、角色、电话。身份在登录时确定，**达人归属和识别留痕都记在这个身份下，归属人同时是待办接收人**。

**模型设置（文本抽取）** —— 仅支持 OpenAI 兼容接口，界面里改完立即生效不用重启。

| 字段 | 说明 |
|---|---|
| Base URL | 如 `https://api.deepseek.com/v1` |
| 模型名称 | 如 `deepseek-chat` |
| **接口形态** | `chat` = `/chat/completions`（国内几家都是这个）；`responses` = `/responses` |
| API Key | 存 `data/settings.json`，留空表示不修改 |
| 并发识别数 | 连续粘多个达人时同时跑几条。触发 429 就调小 |

顶部有 DeepSeek / 通义 / 豆包 / Kimi / 智谱 / 本地 Ollama 一键预设。「测试连接」会显示实际请求的完整 URL 和失败原因（DNS、连接被拒、证书、限流分别有针对性提示）。

单条资料约 2500 输入 tokens，DeepSeek 每条成本约 ¥0.003。

**视觉模型** —— 发货截图识别用，与文本模型分开配。理由：文本高频用便宜模型，视觉低频，而且 deepseek-chat 之类不支持视觉。留空则禁用截图上传。

**寄样产品** —— 录入合作时从这里选。已被合作引用的产品删除时只停用，不影响历史（产品名在合作里是快照，改名不影响已有记录）。

**飞书同步** —— 把合作信息推到公司现用的飞书多维表格，见下节。

**流程设置** —— 回访天数、告知达人话术模板。模板占位符 `{物流}` 会把每个包裹渲染成独立一行「承运商 单号」，多包裹时不会错位。

> `.env` 仍然支持，作为设置的初始值。界面里填的优先级更高。

## 三个角色看到的不一样

以前四个角色的界面完全一样，包括 API Key 设置 —— 仓库不录达人、运营不寄样，
让他们对着一个粘贴框发呆没有意义，把密钥摆在那儿也不合适。

| 角色 | 首屏 | 能做 | 不能做 |
|---|---|---|---|
| 商务 | 粘贴框 + 需要处理 | 全部 | 改别人的合作 |
| 仓库 | 上传发货截图 | 看整张记录表、**给任何人的合作回填快递单** | 录达人、看 API Key |
| 运营 | 已出片 | 只读记录表、取视频链接和口令 | 录入、改任何合作、看 API Key |

**快递单回填故意不卡归属** —— 那本来就是仓库对商务的合作做的动作，卡了就把仓库挡在门外。

归属边界分两类，不要合并成一条规则：

- **私人工作区**（识别任务、草稿）—— 只有本人能读能写，越权返回 **404 而不是 403**，不暴露这个 id 是否存在
- **共享业务数据**（合作、达人）—— 全员可读（记录页的「全部」本来就是这么用的），只有归属人能改

**归属转交**允许两种情形：归属人自己转出，或别人把无人管的记录接到自己名下。
只允许前者的话，商务一离职他名下的达人就永远转不走了。谁转的、为什么转都记在 `ownerHistory` 里。

## 飞书多维表格同步

商务改动合作信息后自动推到飞书，让不进这个系统的人（老板、运营）
在熟悉的地方看到同一份数据。

**这是服务端对服务端的集成**，用应用身份（`tenant_access_token`），
和「飞书扫码登录」是两回事 —— 那个明确不做，这个不需要任何人登录飞书。

### 结构：系统表 + 关联引用

**不直接往团队现用的那张表推。** 那张表是给人看的：列名按团队习惯起、
有多选列、有人工维护的运营字段、还有自动化在写的物流列。
直接推就得迁就它的一切，而它不归我们管 —— 改表的人一动就断，断了没人知道。

改成在同一个多维表格里**新建一张「系统表」，只有程序写它**；
团队表通过飞书原生的**关联 + 查找引用**去取值。

```
  ┌──────────────────┐        ┌────────────────────────────┐
  │  系统表（程序写）  │◄──关联─┤  团队表（人维护）           │
  │  28 列，类型全可控 │        │  查找引用：抖音昵称/单号/…  │
  │  一行 = 合作×产品 │        │  达人等级 / 物流状态 ← 不碰 │
  └──────────────────┘        └────────────────────────────┘
```

引用列是**实时跟随**的：不跑流程、不消耗自动化配额、不会失败。
自动化只负责「系统表新增记录时在团队表建一行并关联」，一条记录一辈子跑一次。

边界因此很清楚：**系统表归程序，团队表归人。我们不写团队表一个字。**

完整方案见 [`docs/飞书同步方案-v2.md`](docs/飞书同步方案-v2.md)。

### 一条铁律

**同步失败绝不影响商务干活。**

业务动作只往出站队列塞一行就返回，真正的推送在后台做。
飞书挂了、断网了、令牌过期了、列名被人改了 —— 商务照样能建档、能回填快递。
失败的留在队列里按 1 分钟起步、逐次翻倍、最长 30 分钟的退避重试。

入队写在 `db.js` 的变更函数里而不是路由层：改动合作的入口有八九个，
靠人记得在每处调一次，迟早会漏掉新加的那个，而漏掉的表现是
「飞书表里这条一直不更新」，很难发现。

### 粒度：一行 = 一条合作 × 一款产品

和团队表的「一次寄样」对齐 —— 一次寄样对应一款产品，所以关联是 1:1，
自动化不用做 1→N 展开（那是它最不擅长的事）。

行标识 `系统ID` = `合作ID#产品行ID`，例如 `cb-00042#ci-00107`。
用产品行的 **id** 而不是数组下标 —— 下标会因增删产品整体错位，
把 A 产品的数据覆盖到 B 那一行，而表现只是「数字不对」，很难联想到是键的问题。

产品行被删掉时，对应的飞书行也会删。这是我们唯一会删飞书数据的地方，两道约束：
**只删 `sync_links` 里记着的 record_id**（手工加的行绝不碰），
且放在最后做（先写该有的再删多余的，反过来中途失败会留下缺口）。

多账号时账号相关的列用「、」拼接 —— 当前全是单账号，代价为零；
真出现矩阵号且需要分别追踪出片时，再考虑加细到 `合作 × 账号 × 产品`。

### 单向

只从本系统推到飞书，不反向读回。

**代价说清楚：被同步的那几列在飞书里手工改，会被下一次推送覆盖。**
所以像「备注」「达人等级」这种只在飞书里维护的列，**不要映射** —— 留空才是对的。

### 怎么知道该新建还是该更新

靠 `系统ID` 那一列（**必填映射**）。没有它每次推送都会新建，
表里会堆重复行，所以配置校验会直接拒绝。

三层兜底：
1. 本地 `sync_links` 表记住 rowKey ↔ record_id
2. 本地映射丢了（换机器、重建库）→ 按系统ID列去飞书搜回来
3. 记录被人在飞书里删了 → 重新建一条，而不是一直重试失败

### 配置

```bash
# 1. 先在飞书里新建一张空数据表
node tools/feishu-inspect.js                    # 找到它的 table_id
node tools/feishu-scaffold.js <table_id>        # 预演，只打印计划
node tools/feishu-scaffold.js <table_id> --apply
```

`feishu-scaffold` **默认预演**，不加 `--apply` 什么都不做；只新建缺的列，
已存在的不改名不改类型不删除，可反复跑；发现 3 列以上不属于系统表定义的列
就拒绝执行 —— 防的是手滑把团队正在用的那张表的 id 贴进来。

然后：设置 → 飞书同步 → 填 App ID / Secret / 表格链接 → 测试连接 → 选表。
**映射会按同名自动匹配**，核对后保存（不保存不生效）。

**测试连接是逐级往下探的**，凭据、Base、表、字段是四个不同的失败原因：

| 卡在哪 | 多半是什么问题 |
|---|---|
| 凭据校验 | App ID / Secret 抄错了 |
| 访问多维表格 | 链接不对，或**应用没被加进这张表** |
| 定位数据表 | 表被删了或换了 |
| 读取字段 | 权限范围不够 |
| 写入权限 | **不验证** —— 见下 |

**测试连接不冒充验证过写入。** 它从头到尾都是读操作，读得通不等于写得进。
最后一级会明确写着「未验证」而不是给一个绿勾 ——
「测试连接说成功、同步却一直失败」是最难受的失败方式。

两个最容易卡住的错误码：

| 码 | 真正的原因 |
|---|---|
| 91403 | **应用没被加进这张表**。在开发者后台申请权限还不够，得打开那张表「…」→「更多」→「添加文档应用」 |
| 1254302 | 进来了但**只有读权限**。查三处：权限范围是不是只读版（改完**必须发版**）、添加文档应用时给的是不是「可阅读」、表是否开了高级权限（文档级授权不继承） |

两者容易混：91403 是压根进不来，1254302 是进来了只能看。
翻成同一句话会让人反复去确认「添加文档应用」，而那一步早就做过了。

### 列类型只用四种

系统表的列由我们建，只用多行文本 / 数字 / 日期 / 复选框。

**刻意不用单选和多选** —— 它们要求写入的值必须已存在于选项里，否则报 1254043。
每上一个新品就得记得去飞书加选项，忘了就同步失败。
这种「平时没事、关键时刻炸」的依赖不值得为了好看引入。

值仍会按目标列类型转换后再写（数字列给数字、日期列给毫秒时间戳、
复选框给布尔、超链接给 `{text, link}`）—— 类型不对飞书报 1254002 且不说是哪一列。
映射界面只列出**可写**的列，公式、自动编号、创建时间那些是只读的。

空值不写入，而不是写个空字符串把飞书里已有的内容覆盖掉。

### 同步状态看得见

合作记录表有「飞书同步」一列：

| | 含义 |
|---|---|
| 未启用 | 同步没开或没配完 |
| 未同步 | 从没推过，多半是开启同步之前的老记录 |
| 待同步 | 在队列里等推送 |
| 已同步 | 飞书里有对应的行（悬停看时间和行数） |
| 同步失败 | 重试到上限，需要人介入 |

「未同步」和「同步失败」刻意用不同颜色 —— 混成一个灰点的话，
表里几十条灰的会把真正坏掉的那条淹没。

**状态是从 `outbox` + `sync_links` 推导的，不在合作表上存一份。**
存一份就要在每个改状态的地方记得更新它，迟早漏一处，
而漏掉的表现是「界面说已同步、飞书里其实没有」—— 比不显示更糟。

点开合作详情能看到失败的**原始原因**并手动重推，不受退避约束
（点按钮就是在说「现在试」，而且多半刚去飞书那边把权限或列名修好了）。

### 环境变量

`FEISHU_BASE` 可覆盖接口根地址：回归测试指向本地假服务，
国际版 Lark 用 `https://open.larksuite.com/open-apis`。

## 日志

两种，用途不同，**不要混着看**：

| | 回答什么 | 在哪 |
|---|---|---|
| 操作日志 | 谁在什么时候动了什么 | 设置 → 运行日志 |
| 错误日志 | 哪里坏了、怎么坏的 | 同上 + stderr |
| `intake_logs` | 模型抽出什么、人改成什么 | 合作详情 → 时间线 → 建档 |

第三个是语料，不是日志 —— 三者合并任何两个都会让第三个用途变难。

### 自动记录，不靠人记得

**所有非 GET 请求**在 `server.js` 的请求处理外层留下一条，路由自己不做任何事。

指望每个路由都记得调一次 `log()`，迟早漏掉新加的那个，
而漏掉的表现是「这条记录谁改的查不到」—— 等到需要查的时候才发现没记，
已经晚了。和 `markDirty` 放在 db 层是同一个理由。

**GET 不记。** 读操作记进去只会把有用的淹掉。

**失败的操作也记**，标成 `ok=false`。「谁试图删了别人的记录但被拦住了」
和「谁删成功了」都值得留痕；只记成功的话，被拦住的尝试完全看不见。

`action` 存的是**路由模板**（`POST /api/collaborations/:id/status`）而不是
实际路径 —— 存实际路径的话，「改状态这个动作一共发生过几次」永远算不出来。
具体 id 单独存在 `target` 列，两种查法都成立。

### 不记什么

**请求体一律不入库。** 里面有达人的真实姓名、手机号、地址，
还有 API Key 和团队口令。日志的价值是「谁动了哪条」，不是「改成了什么」
—— 后者去看记录本身或 `intake_logs`。

错误的 message 和 stack 会存，但**先过一遍脱敏**：手机号打码、
`sk-` / `Bearer` 开头的密钥、以及 `apiKey` / `appSecret` / `passphrase` /
`password` / `token` 这些键名后面的值全部抹掉。

在写入时脱敏而不是展示时 —— 日志的权限比业务数据低（排查的人不一定是归属人）。

### 两个不对称的选择

**错误日志留最近 1000 条，操作日志不设上限。**
错误会成片爆发（飞书挂一整晚能刷出几千条同样的错），留着不帮忙定位；
而操作日志是**账**，剪掉就失去意义。

**记日志永不抛异常。** 它是被业务动作顺手触发的，抛出去会污染那次操作的结果 ——
因为写不进日志而让商务的「确认寄样」失败，是拿一件小事去毁一件大事。
有测试专门制造真正会抛的场景来守这条。

**错误同时写 stderr。** 表里那份是给界面看的；数据库打不开的时候
表里写不进去，而那种情况恰恰最需要日志。

### 进程级兜底

没被 catch 住的异常和 Promise 拒绝记一条日志后**继续跑，不退出进程**。

launchd 的 `KeepAlive` 会把崩溃的进程拉起来，但那意味着正在处理的请求全断。
记下来继续跑对 6 个人的团队更实用 —— 代价是可能带着一个坏掉的状态继续服务，
所以这条日志在界面上是红的。

## 设计取向

**不追求识别精度，追求「错误商务看得见」。**

商务的二次确认是流程的固有环节，所以判断标准是：**这个错误商务肉眼能不能发现？**

- **能发现**（字段名认错、姓名地址切分不准）→ 扫一眼就改，不投入工程成本
- **发现不了** → 系统必须兜住

系统兜住的四类：

| 静默错误 | 处理 |
|---|---|
| 跨平台 ID 混入抖音字段 | 提示词隔离 + `rules.js` 二次拦截（视频号 ID 形态检测），转存到「其他平台账号」 |
| 合作码前导零丢失 | 全链路字符串，从提示词铁律到入库都禁止转数字 |
| 字段残缺被卡死 | 校验按动作分级，见上 |
| UID 与合作码填反 | 两者同为 11 位纯数字时并排展示，给一个**「两者互换」**按钮 |

查重按蓝图 §18.9：抖音号 / UID 精确匹配即拦截（409），带出归属商务和历史合作次数；手机号相同只做弱提示。**查重永远跨商务**，否则「已归属其他商务」这条规则无法工作。**强制创建已移除** —— 与「达人归属固定、禁止重复创建」直接冲突。

## 目录结构

```
server.js               HTTP 服务、API 路由、全局登录守卫、静态文件、.env 读取

lib/db.js               数据层 —— 换存储只改这一个文件
lib/store.js            SQLite 引擎：建表、索引、事务、发号
lib/import-json.js      db.json → SQLite 的一次性导入器
lib/auth.js             团队口令哈希、会话签名、cookie

lib/rules.js            确定性规则：输入路由、口令解析、校验分级、
                        合作类型判定、静默错误检出、待办推导
lib/feishu.js           飞书 API 客户端：令牌、字段、记录、错误码翻译
lib/feishu-schema.js    「系统表」列定义 —— 飞书那张表长什么样，唯一真相来源
lib/sync.js             同步业务侧：取值、行展开、出站队列、退避重试、状态推导
lib/logs.js             操作日志与错误日志：写入、脱敏、查询、进程级兜底
lib/shots.js            发货截图存档：落文件不落库、路径白名单、数量上限

public/index.html       结构与样式（含登录屏）
public/app.js           前端逻辑

tools/feishu-inspect.js   只读，打印飞书表的结构（排查用）
tools/feishu-scaffold.js  按 schema 建列，**默认预演**，加 --apply 才动手

tests/                  node:test 回归，零依赖
docs/                   部署手册、数据结构、飞书方案

data/naimeng.db         业务数据（含达人 PII）—— SQLite，WAL 模式
data/settings.json      配置（含 API Key、团队口令哈希、飞书凭据）
data/.session-secret    会话签名密钥 —— 删掉它 = 踢所有人下线
data/shots/             发货截图存档，保留最近 1000 张
data/backups/           启动时自动备份，保留最近 7 份
```

`data/` 整个目录在 `.gitignore` 里，**永远不要提交**。

**三条不可越界的规则**：

1. **身份只有一个入口** —— `userOf(req)`。它现在读会话 cookie。其他地方不得出现第二种「当前用户」取法。
   这条规则的价值已经兑现过一次：从「读请求头」改成「读签名会话」时，**只改了这一个函数**。
2. **数据访问只有一个出口** —— `lib/db.js`。对外全部 async，换 SQLite / Postgres 时 `server.js` 一行不动。
3. **业务规则不碰存储** —— `lib/rules.js` 保持纯函数，实测零 IO 依赖。

**抽了就要有出口。** 模型抽到的值必须一路能走到界面上 ——
中间任何一环（`normalize` 不输出、`sanitizeForStore` 不保留、路由不传）
断掉都不会报错，只表现为「那个字段永远是空的」。
`cooperation_type` 和 `sales_channel` 都这么丢过一次，各有测试守着整条链路。

**同一份定义不写两遍。** 飞书的列定义只在 `lib/feishu-schema.js` 里，
`sync.js` 的可映射字段由它派生，假服务的列表也由它生成，
模块加载时校验每一列都有取值函数、缺了直接抛。
这条是踩出来的：列定义和取值函数各维护一份时，加了列忘了加函数不会报错，
只表现为「那一列永远是空的」，四个字段就是这么丢的。

**分层原则**：`agent.js` 只负责把非结构化文本变成候选值；校验、清洗、消歧、查重全在 `rules.js` 用确定性代码做。模型换掉、提示词改了，正确性保证不受影响。

**「当前用户」不存在全局变量里。** 设置页的「我的资料」改的永远是会话对应的那个人，
请求体里就算带了 id 也不看 —— 让客户端指定改谁，等于把越权做成一个请求参数。
`settings.json` 里那个全局的 `user` 键已经删除：它曾让商务甲看到并改到商务乙的资料。

### 测试要能证伪

新增和改动的测试都做过**变异验证**：把 bug 放回去，确认测试真的会红。

这不是形式主义。有两条测试曾经是装饰品：

- `assert.equal(typeof agentReady(), 'boolean')` —— 只验类型不验值。
  `agentReady()` 永远返回 `false` 它也照样绿，于是「模型配置静默失效」这个真实回归溜了过去
- 裸链接那条断言在匹配一个具体的旧字符串，换个写法就抓不到

现在的写法是断言**性质**：`renderVideo` 不允许任何提前 `return`、
确认按钮必须在函数顶层缩进、配置齐全后 `agentReady` 必须为 `true`、
用到的 `.st.xxx` 类名必须在 CSS 里真实存在。

**能执行就执行，不要只搜源码。** `esc()` 那条测试把函数抽出来
`new Function` 真跑一遍 —— 上一版只检查映射表里有没有 `"'": '&#39;'`，
而把正则从 `[&<>"']` 改回 `[&<>"]` 时映射表原封不动，断言照样绿。
**映射表里有 ≠ 正则会匹配到。**

最近一次变异验证抓到的漏网之鱼值得记一笔：加「不寄样合作」时做了六项变异，
五项都红了，唯独「不寄样也落成待寄样」是绿的 —— 初始状态当时没有任何测试覆盖。
**全绿不代表你关心的那一行被测到了**，这就是为什么要做变异验证。

断言也要有对照组。「不寄样的合作不催产品、不催快递单号」这条配了一个
同样数据换成寄样合作的用例，否则那两条断言可能只是因为 `buildTodos` 整个没跑。

## 鉴权

**一道团队口令 + 服务端签发的身份。** 不依赖任何外部服务，断网照常登录。

选这个方案是因为威胁模型很具体：系统跑在办公室局域网，同网段任何设备都能连上，
而库里有达人的真实姓名、手机号、收件地址。团队只有 6 个人且同处一间办公室，
所以不需要每人一套密码体系 —— 挡住「不该在这个网段上的设备」就覆盖了真实风险。

| 环节 | 做法 |
|---|---|
| 口令 | scrypt 加盐哈希，不存明文 |
| 身份 | HMAC 签名的 HttpOnly cookie，有效期写在载荷里**参与签名** |
| 名单保护 | 口令验过之前不返回团队成员姓名 |
| 踢人下线 | 删掉 `data/.session-secret` 重启，所有会话立刻失效 |

**身份必须由服务端签发，不能让前端自报。** 早先版本把 userId 存在 localStorage
再塞进 `X-User-Id` 请求头 —— 改个请求头就能变成任何人，那些按归属拦截的 403 形同虚设。
还有一处更隐蔽：无身份时会回落到全局 `settings.user`，
意味着任何未登录请求都自动获得「最后一个保存过身份的人」的权限。

### 已知的边界

- **局域网内是明文 http**，会话 cookie 在同网段可被嗅探。启动横幅里每天都会提醒这一条
- **口令是共享的**。登录时要从名单里选自己是谁，操作日志记的就是那个身份 ——
  所以「谁做的」是能查的；但口令共享意味着**拦不住冒充**，
  想赖账的人可以用别人的名字登录。团队扩大或需要不可抵赖的证据时，该换成每人一套凭据

## 数据

`data/naimeng.db` 业务数据（SQLite）、`data/settings.json` 配置。分开存的理由：**两类数据处置方式不同 —— 业务数据要备份要迁移，密钥不能跟着走**。整个 `data/` 都在 `.gitignore`。

**启动时自动备份**到 `data/backups/`，保留最近 7 份。WAL 模式下会先 checkpoint 再拷贝，
否则可能漏掉还留在 WAL 里的最新事务。

**从 JSON 迁移是自动的**：首次启动发现 `data/db.json` 就一次性导进 SQLite，
**原件不删**（出问题能对账、能重来），并在 store 的 meta 里记下来源，重复启动不会再导 ——
否则第二次启动就会用旧快照盖掉新录的数据。

> 备份文件和数据库在**同一块硬盘**上。硬盘坏了一起没，必须往外拷一份，见部署文档第 9 节。

首次用新版启动会自动跑 v1→v2 迁移（达人内嵌的收件信息拆成「达人默认值 + 合作快照」）。

`accounts.uid` 与 `accounts.cooperationCode` 一律**字符串**，任何存储后端都不要用整数类型 ——
合作码可能以 0 开头，UID 有 20 位（超过 `Number.MAX_SAFE_INTEGER`）。
`lib/store.js` 在入库前强制 `String()`，并有测试专门喂 Number 验证这条防线。
