# 飞书同步映射设计 v1

对接目标：多维表格 `BZHJbRYP9aMsXisYD2QcnpLqnke` / 表 `tbl2zfl51fVdGq5n`（达人寄样信息）

读表结果与业务确认见本文附录。这份文档记录**为什么这么映射**，
而不只是映射成什么 —— 后面有人想改某一列时，先看这里有没有说过它的代价。

---

## 一、粒度：一行 = 一条合作 × 一款产品

这是整个设计里唯一的结构性决定，其余都跟着它走。

**业务事实**：飞书表里一行是「一次寄样」，而一次寄样对应一款产品。
同一个商务、同一个达人、同一个收货地址会出现多行 —— 差别只在产品。
表里那列「重复检测」（双向关联）正是为这种情形准备的。

**我方模型**：一条合作有 `items[]`（产品行）和 `fulfillments[]`（账号）。

所以推送要在 `items` 上展开：**一条合作有几款产品就推几行。**

### 行标识

系统ID 列存复合键：

```
cb-00042#ci-00107        合作ID # 产品行ID
```

用产品行的 `id` 而不是数组下标 —— 下标会因为增删产品而整体错位，
把 A 产品的数据覆盖到 B 产品那一行去。这类 bug 出现时表面上只是
「数字不对」，很难联想到是键的问题。

### 账号怎么办

「抖音昵称」和「id」在飞书表里各是一列（单数），而我方一条合作可以挂
多个账号（达人的矩阵号）。**多账号时用「、」拼在一格里。**

代价说清楚：这种情况下「拍摄进度」「发布链接」也是拼接的，
看不出哪个进度属于哪个号。当前库里 4 条合作全是单账号，
这个代价暂时是零；等真出现矩阵号且需要分别追踪时，
再考虑把粒度加细到 `合作 × 账号 × 产品`。

**先不加细。** 现在就按三维展开，会让单账号（也就是绝大多数）的
情形凭空多出一层复杂度，而收益是零。

## 二、映射表（13 列）

| 飞书列 | 类型 | 我方字段 | 说明 |
|---|---|---|---|
| **系统ID** ★ | 多行文本 | `rowKey` | `合作ID#产品行ID`，必填 |
| 日期 | 日期 | 建档时间 | |
| 抖音昵称 | 多行文本 | **账号昵称** | 不是「达人名称」，见下 |
| id | 多行文本 | 抖音号 | 已确认存的是抖音号 |
| 地址 | 多行文本 | **收件信息（合并）** | 姓名 + 电话 + 地址拼一段 |
| 寄样产品 | 多选 | **本行产品名** | 数组，见「多选列」一节 |
| 数量 | 数字 | **本行数量** | |
| 是否寄样 | 多行文本 | 由状态派生 | 待寄样→「否」，其余→「是」 |
| 寄样成本 | 多行文本 | **寄样费用（仅首行）** | 见下 |
| 快递单号 | 多行文本 | 快递单号 | 多包裹用「、」连 |
| 拍摄进度 | 多行文本 | 拍摄进度 | 待拍摄/已催拍/已发布/本次不出片 |
| 发布链接 | 多行文本 | 视频链接 | 多条换行 |
| 归属人 | 多选 | 归属商务 | 数组 |

★ = 必填。

### 「达人名称」用的是账号昵称

飞书表里的「抖音昵称」，业务上就当达人名称用。
我方 `creators.name`（达人名称）和 `accounts.nickname`（账号昵称）
是两个字段，绝大多数时候一样，但矩阵号时不一样。

**映射到 `accounts.nickname`** —— 飞书那列叫「抖音昵称」，
名副其实优先于我方的内部区分。

### 收件信息合并成一段

飞书表只有「地址」一列，业务上把收件人、电话、地址合在一起看。
所以我方拼成：

```
张某某 13800138000 某省某市某路 1 号
```

**这一列含真实达人的姓名和手机号。** 谁能看这张表就等于谁能看这些
—— 和系统里的权限是两套，需要各自确认。

### 寄样费用只写第一行

`sampleCost` 是**整条合作**的费用，而我们按产品拆成了多行。
每行都写会让飞书里的求和统计翻倍。

**只写到第一行（产品行 id 最小的那行），其余留空。**
这不完美：看第二行的人会以为这次寄样没花钱。但相比一个悄悄虚高的
合计数，「有一格是空的」是更容易被发现、也更容易问清楚的问题。

单产品时不存在这个问题，而当前全部是单产品。

## 三、不映射的列，以及为什么

**五列由自动化在写，碰了会打架：**

```
物流状态 · 物流状态.签收时间 · 最新物流信息 · 物流轨迹 · 查询时间
```

这几列的形态是快递查询机器人或飞书自动化在维护。我们是单向推送，
写进去就会覆盖它，然后它再写回来 —— 两边互相打架，而现象是
「数据一会儿对一会儿不对」，极难排查。**一列都不映射。**

**四列是人在飞书里维护的运营信息，系统里没有对应事实：**

- 达人等级（多选）
- 是否发投（单选）／是否已投（多选）—— 投流环节，系统目前不管
- 备注（多选）

**三列是只读类型，飞书本身就不允许写：**

- 重复检测（双向关联）
- 父记录 2 / 父记录 3（关联）

**明确忽略（业务确认）：** 合作状态、快递公司、已告知达人。

> 单向推送的铁律：**凡是映射了的列，在飞书里手工改都会被下次推送覆盖。**
> 所以「不映射」不是遗漏，是把那一列的所有权留给飞书。

## 四、要改的代码

### 1. `coerce()` 缺多选（type 4）—— 现在推必然失败

飞书的多选列要的是**数组**，我方现在走默认分支返回字符串。
这张表有五列是多选，其中「寄样产品」「归属人」都在映射表里。

```js
case 4:  // 多选：要数组，不是字符串
  return Array.isArray(value) ? value.map(String)
       : String(value).split(/[、,，]/).map(s => s.trim()).filter(Boolean);
```

**还有一层**：多选/单选的值必须**已存在于该列的选项里**，
否则飞书报 1254043。产品名和商务姓名都可能是选项里没有的。
这个错误码要翻译成「『洁齿冻干』不在飞书那一列的选项里，
去飞书把它加进选项，或把这一列改成多行文本」。

### 2. 推送单位从「合作」改成「合作 × 产品行」

改动集中在 `lib/sync.js`：`buildFields` 之上加一层展开，
`pushOne` 按 rowKey 而不是合作 id 去找记录，`sync_links` 的
`entityId` 存 rowKey。

**出站队列仍按合作入队** —— `db.js` 里的 `markDirty(collaborationId)`
不动。展开发生在推送时，因为「有几行」是随产品行增删变化的，
入队时算出来会过期。

### 3. 删产品行要能删掉对应的飞书行

新增的情形：合作从 2 款产品改成 1 款，飞书里那一行成了孤儿。
需要在推送时对比 `sync_links` 里已有的 rowKey 和当前应有的，
多出来的调删除接口。

**这是第一次往飞书写「删除」。** 之前只有新建和更新，
最坏后果是多一行；现在最坏后果是删错行。所以按 record_id 精确删，
并且只删 `sync_links` 里我们自己建过的 —— 手工加的行绝不碰。

### 4. 新增 SOURCE_FIELDS

`accountNickname`、`recipientFull`、`itemProduct`、`itemQuantity`、
`sampleCostFirst`、`shipped`（是否寄样）。

`get()` 的签名要从 `(cb)` 变成 `(cb, item)`。

## 五、上线前必须做的

1. **先在一张复制表上跑通**，别直接对着同事在用的表试。
   飞书表可以「复制副本」，改一下配置里的 table_id 即可。
2. 确认「寄样产品」「归属人」两列的**选项里有需要的值**，
   或者把它们改成多行文本（推荐 —— 多选列的选项维护是长期负担）。
3. 表里已有的历史行**没有系统ID**，第一次推送会全部新建，
   和历史行并存。要么接受（历史归历史），要么先人工回填系统ID。
   **这一条得提前想好，推完再想就晚了。**
