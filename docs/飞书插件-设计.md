# 飞书侧边栏插件 · 设计

可达性已验证通过，见 `飞书插件-可达性验证.md`。这份是「做什么、不做什么」。

---

## 一、先把一件事定死：插件和入站同步是二选一

之前讨论「商务不肯用 web 端」时，我提过**按字段划分所有权**——
达人档案字段归飞书写，流程字段归系统写。那是为「商务坚持在表格里直接敲」
准备的兜底方案。

**插件成立之后，那条路不该再走。**

理由不是嫌麻烦，是**两个都做就有两个写入者**。同一个达人，
可能从插件进来一次、从飞书那张表回流一次，然后系统要回答
「这两条是不是同一个人、谁赢」。这正是当初决定不做双向同步的原因，
它不会因为多了一个插件而变简单。

所以：

> **数据只有一个方向：插件 → 系统 → 飞书系统表。**
> 团队那张表继续归人，系统永远不读它。

「系统表归程序、团队表归人」这条边界不变，插件只是给系统加了一个入口。

## 二、插件做什么

商务在飞书里的动作只有三件，插件就做这三件：

| | 输入 | 产出 |
|---|---|---|
| 达人建档 | 微信里粘来的一坨文本 | 走现有 `POST /api/route` → `/api/jobs` 识别 → 确认入库 |
| 快递信息 | 单号，或发货截图 | 现有 `POST /api/shipments/confirm` |
| 出片信息 | 视频链接 / 本次不出片 | 现有 `POST /api/video/submit` |

**不做的**：合作列表、合作详情、日志、设置、产品管理、我的资料。
那些留在 web 端。侧边栏就 560px 宽，塞进去只会两边都难用；
而且商务在飞书里根本不做那些事。

## 三、插件存在的第一理由：查重

这不是「顺便也能查重」，这是插件相对于「让商务直接在飞书里敲」
的**唯一不可替代的能力**。

现在那张表里的「重复检测」列已经有一大片「重复」标记。
飞书的公式是**事后**告诉你重复了——人已经敲完一整行了。
而且它只能比字符串，比不出「这个抖音号属于的达人，三月份张三建过档、合作过两次」。

插件在商务贴完抖音号的那一刻就能调 `db.findConflicts`：

- **硬冲突**（uid / 抖音号命中）→ 直接拦，显示原记录归属谁、合作过几次
- **软提示**（收件手机号相同）→ 不拦，提示「可能是同一个人的另一批账号」

这个能力**纯同步方案拿不到**——同步是事后的，插件是事前的。

## 四、认证：必须解决，而且不能让商务粘令牌

验证里最反直觉的一条：**同源了，cookie 还是带不上**。
`SameSite` 看的是顶层站点（`feishu.cn`），不是 iframe 自己的源。

所以插件只能走 `Authorization: Bearer`。但**不能指望商务去 web 端签一个令牌
再粘进来**——那比让他们用 web 端还麻烦，方案就白做了。

### 方案：插件里做一次口令登录，换一个长期令牌

新增一条路由：

```
POST /api/auth/token   { passphrase, userId }  →  { token }
```

复用 `POST /api/auth/login` 那套校验（口令 + 选自己是谁），
只是**发的不是 `Set-Cookie` 而是一个 API 令牌**。
签发路径完全复用 `issueApiToken`，令牌清单照样进 `settings.apiTokens`，
照样能吊销。

> 为什么不给 `/api/auth/login` 加个开关而是新开一条：
> 一条路由发两种凭据，将来一定会有人在调用点上看错。
> 「web 会话和 API 令牌不能互换」这条约束在 `k` 字段上花了力气，
> 不该在路由层重新混起来。

### 令牌存哪：**这是最大的未解风险**

插件是第三方 iframe，`localStorage` 在这个上下文里：

- Chrome 默认会给它**分区存储**（按 顶层站点 + frame 源），能读能写，分区稳定
- 但用户如果**屏蔽第三方 cookie**，浏览器会连 `localStorage` 一起拒绝，**抛异常**
- 飞书**客户端**里是什么行为，不知道

这和「同源了 cookie 还是不带」是**同一个根因家族**：
第三方上下文里的存储不归你说了算。

**必须先验，不能先写。** 一次探针就能测：写一个值、刷新、读回来。
如果不可靠，退路是用 bitable SDK 自己的存储（`bitable.bridge` 有持久化接口，
但具体能力待查），最差的退路是每次开插件重新输一次口令——
可用，但每天输一次会让人烦到不用。

## 五、要不要引 bitable SDK

引了才能拿到「当前选中的是哪一行」。这是插件相对 web 端唯一的**增量**能力：
商务点表格里某一行 → 插件直接显示那条对应的系统记录。

代价是破坏「零依赖、不要构建」。可接受的做法是**从 CDN 引 UMD 构建**，
不引入 npm 和构建步骤。

**待查**：`@lark-base-open/js-sdk` 有没有可直接 `<script>` 引的 UMD 产物。
没有的话，这个能力先不做——它是加分项，不是前提。三件录入的事不需要它。

## 六、开工顺序

1. **补两个探针项**：第三方上下文里 `localStorage` 能不能用；SDK 有没有 UMD
   —— 两个都是「先写完才发现不行」代价最高的
2. **`POST /api/auth/token`** —— 几十行，有了它插件才能自己站住
3. **达人建档一条流程走通** —— 粘贴 → 识别 → **查重拦截** → 入库
4. 快递、出片两条 —— 复用现有路由，主要是界面
5. 让一个商务真用一周，再决定 web 端还留不留达人建档

第 3 步做完就该拿给人试。**先做完五件事再给人看，是这个项目最该避免的做法**——
「商务不肯用 web 端」这个问题本身就是这么憋出来的。
