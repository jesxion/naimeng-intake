# 架构选型：要不要把 naimeng-intake 做成 DeepSeek Harness 的插件

**结论：不要。但你的顾虑是对的，只是解法不是它。**

判断依据是读过 `deepseek-harness` 的 `README`、`docs/architecture.md`、
`docs/cookbook/extension-cookbook.md`，不是凭名字猜的。

---

## 一、dsh 到底是什么

先把事实摆清楚（截至 2026-08 查证）：

- DeepSeek AI 出品，MIT 许可，204k star
- README 里**加粗全大写**写着 `THERE WILL BE COMPATIBILITY-BREAKING CHANGES`，
  自称 developer preview
- 建在 Cordis 之上，pnpm monorepo + TypeScript + 构建步骤 + vendored 依赖 + native 模块
- 定位是 **agent harness**

它的架构确实漂亮：没有特权内核，模型适配器、工具注册表、会话日志、
甚至 agent loop 本身都是插件，每个都能从配置里换掉。

## 二、决定性的证据：它的扩展点里没有「业务」

`architecture.md` 的「Where new behavior goes」和 cookbook 的
「feature → mechanism」两张表，加起来三十多行，**没有一行**是关于：

- 业务实体 / 数据表 / CRUD
- 表单、列表、详情这类非对话界面
- 按记录的归属权限
- 业务动作的审计
- 出站同步到外部系统

有的全是：模型适配器、工具注册、shell 执行、终端、沙箱、审批、
子代理、压缩、计划模式、钩子、MCP、cron。

**UI 那一行尤其说明问题**：

> Add UI or editor integration | drive `ctx.agents` and render from `session/event`
>
> Web Client Chat business node | register a `ConversationNodeDefinition` + 键控渲染器

也就是说，dsh 的「界面」是**对话界面**。往里加东西的形态是「聊天流里的一种消息节点」。
合作记录那张八列的表、五张卡片的抽屉、点击复制的那些行 —— 在这个模型里没有位置。

`SessionEventMap` 那套「durable session state」是**会话状态**，
不是业务数据。session log 的用途是「模型看到的上下文必须能从日志重建」。
达人、合作、包裹不属于这个范畴。

## 三、算一笔账

按当前代码分：

| 层 | 行数 | dsh 能帮上忙吗 |
|---|---|---|
| `agent.js` LLM 调用、提示词、降级 | 634 | **能**，这块正是它的强项 |
| `store/auth/logs/shots` 基础设施 | 677 | 不能，它没有对应的东西 |
| `db/rules/sync/feishu` 业务 | 2749 | 不能 |
| `server.js` + 前端 | 4463 | 不能，而且形态冲突 |

**它能替代的是 634 行，而要为此重写或迁就的是 7889 行。**

而且那 634 行现在是零依赖、能离线降级、行为完全可控的。

## 四、还要付的三笔代价

**部署从「拷贝一个目录」变成一条构建链。**
现在是 `node server.js`，launchd 拉起，断网照常跑，Mac mini 上放着不用管。
换成 dsh 就要 pnpm、build、lock 文件、native 模块的平台匹配。
对一个**由一个人维护、跑在办公室一台机器上**的系统，这是实打实的负债。

**承重层变成 developer preview。**
这套系统承载的是公司真实业务。「某天 pull 完起不来，而当天商务要录 20 条」
不是抽象风险 —— 人家自己在 README 里用大写警告过了。

**控制反转。**
现在是我们的进程启动、我们决定生命周期。变成插件之后是
`dsh --profile web` 启动那棵 Cordis 树，我们的东西挂在上面。
排查问题时的第一层永远是「是 dsh 的问题还是我们的问题」。

## 五、你的顾虑是对的，真问题在别处

「不具有架构式的可持续」背后的真问题是：

> 下一个模块（投流 / 财务 / 供应链）来的时候，是不是又要从零写一个 server.js？

这确实要解决。但解决它不需要 agent 宿主，需要的是**把已经和业务无关的那 677 行拎出来**。

`store.js`（SQLite 引擎、热列+JSON、事务、发号）、`auth.js`（口令、会话签名）、
`logs.js`（操作日志、错误日志、脱敏）、`shots.js`（附件存档、路径白名单）——
这四个文件里没有一行提到达人、合作、寄样。它们已经是通用基础设施了，
只是恰好放在同一个仓库里。

再加上现在还嵌在业务里、但本质通用的两样：

- **出站队列 + 退避重试**（`sync.js` 的前半段）：任何模块要同步到外部系统都用得上
- **归属权限模型**（`ownerOr403` + `ownerUserId`）：任何模块都要回答「谁能改这条」

抽出来大约 900～1100 行，**零新增依赖**，第二个模块直接 import。
这是共享库的路子，工作量比插件宿主小一个数量级，
而且**不引入任何会破坏兼容的外部依赖**。

## 六、但 dsh 有一件事值得做，而且零风险

**把 naimeng-intake 暴露成 MCP server。**

dsh 的 cookbook 里 MCP 是一等公民：

> MCP | one plugin per server: discover tools → `ctx.tools.register()`

这意味着：

- 现在这套系统**一行架构不改**，继续 `node server.js` 跑着
- dsh 能调它，Claude 能调它，将来别的宿主也能调它
- **不绑定任何一家**。dsh 破坏兼容了，换一个宿主就是了
- 真正的好处是：可以做「问一句就查到」的内部助手 ——
  「豆豆的小窝上次寄样是什么时候」「这周还有几条没回填单号」

工作量：一层 MCP 适配，复用现有路由，几百行。
换来的是**可逆性** —— 这是这个决策里最值钱的东西。

## 七、建议的顺序

1. **抽共享核**（`naimeng-core`）—— 无论走哪条路都要做，而且现在做最便宜
2. **MCP 适配** —— 拿到可逆性，随时可以接任何 agent 宿主
3. **想试 dsh 就试** —— 用 MCP 接，试坏了业务不受影响

**不建议**：把业务系统改造成 dsh 插件。

## 八、什么情况下这个结论会翻

我判断的前提是「更多业务模块，人操作 + AI 辅助」。如果方向变成
**让 agent 端到端跑流程**（自己查物流、自己写飞书、自己催达人，
人只在关键节点确认），那 harness 就是对的形态。

但即使那样，**也不是把现在这套塞进去**，而是：
现在这套继续当业务系统 + 数据源（通过 MCP 暴露），
harness 那边是一个新的、独立的东西。

两者的边界应该像现在「系统表归程序、团队表归人」一样清楚。
