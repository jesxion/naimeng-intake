# 数据结构

SQLite（`node:sqlite`，无 ORM）。18 张表 + 一个 `data/settings.json`。

这份文档的目的是让接手的人不用翻代码就知道数据长什么样、为什么这么放。
**字段清单会过时，设计理由不会** —— 所以每张表后面都写了「为什么」，
改结构时先看那一段。

字段清单随时可以重新生成：

```bash
node --experimental-sqlite -e "
const {DatabaseSync}=require('node:sqlite');
const d=new DatabaseSync('data/naimeng.db',{readOnly:true});
for(const t of d.prepare(\"select name from sqlite_master where type='table' order by name\").all())
  console.log(t.name, d.prepare('pragma table_info('+t.name+')').all().map(c=>c.name).join(', '));
"
```

## 一、存储模式：热列 + JSON

每张表都是这个形状：

```sql
CREATE TABLE accounts (
  id TEXT PRIMARY KEY,
  creatorId TEXT,          -- 热列：要关联
  uid TEXT,                -- 热列：要查重
  douyinId TEXT,           -- 热列：要查重
  nickname TEXT,           -- 热列：要搜索
  cooperationCode TEXT,    -- 热列：要查重
  data TEXT                -- 其余字段整体存 JSON
);
```

**会被查询、排序、关联的字段独立成列并建索引，其余塞进 `data`。**

这么做的理由：查重、按归属过滤、按合作关联这些热点路径走真索引，
不再全表扫；而新增一个只是「存着给人看」的字段不用改表结构。
将来某个字段需要查询了，再把它从 JSON 里提成列 —— 是渐进的，不用一次做完。

**代价**：JSON 里的字段没法在 SQL 里过滤。真需要时就提成列，
`store.js` 里 `put()` 会同时写热列和 JSON，两边不会分叉。

> 一个踩过的坑：`put()` 里对热列强制 `String(v)`。
> 少了这一步，一个数字类型的 uid 会和字符串 uid 查不到一起，查重就失效。

> **热列名字要避开 SQL 保留字。** 错误日志那一列本来想叫 `where`，
> 建表直接报 `near "where": syntax error` —— 而那句话完全看不出是哪一列，
> 只能靠二分注释去找。现在叫 `source`，并有测试扫全部热列名。

## 二、关系全景

```
                         users (8)
                            │ ownerUserId
              ┌─────────────┴─────────────┐
              ▼                           ▼
         creators ─────────────────► collaborations
          「达人」    creatorId          「一次合作」
              │                            │ collaborationId
              │ creatorId      ┌───────────┼───────────┐
              ▼                ▼           ▼           ▼
         accounts        collab_items  collab_accounts  packages
        「抖音账号」       「产品行」    「履约项」      「包裹」
              │                │           │
              │                │ productId │ accountId
              │                ▼           │
              │           products         │
              └────────────────────────────┘
                     履约项指回具体账号

     other_accounts ← creatorId    非抖音平台账号，已建表未启用
```

一句话：**达人有多个抖音账号；每次合作绑定其中若干个账号（履约项）、
若干款产品（产品行）、产生若干个包裹。**

## 三、核心六张表

### `creators` —— 达人

```
id, name, ownerUserId, channel, defaultRecipient, remark, createdAt, updatedAt
```

| 字段 | 说明 |
|---|---|
| `ownerUserId` | 归属商务。**权限的基础** —— 按 id 直取的接口都要校验它 |
| `channel` | 来源渠道，默认「抖音达人广场」 |
| `defaultRecipient` | 默认收件信息 `{name, phone, address, deliveryNote}` |

**为什么达人和账号分开**：一个达人可能有矩阵号（主号 + 若干小号），
寄一次样但要在多个号上出片。合在一张表里就没法表达。

### `accounts` —— 抖音账号

```
id, creatorId, nickname, douyinId, uid, cooperationCode, profileUrl, createdAt
```

三个都是标识符，各有各的用途：

| 字段 | 是什么 | 注意 |
|---|---|---|
| `douyinId` | 用户可见的抖音号 | |
| `uid` | 抖音内部数字 ID | |
| `cooperationCode` | 星图合作码 | **可能有前导零，必须当字符串** |

`nickname, douyinId, uid, cooperationCode` 四列都建了索引 —— 建档时
要拿这几个值去查重「这个达人是不是已经建过了」。

> 前导零这件事有测试守着（`store.test.js`）。曾经的测试全喂字符串，
> 而 `String(v)` 对字符串是空操作 —— 等于什么都没测。现在喂的是数字。

### `collaborations` —— 一次合作

```
id, creatorId, ownerUserId, type, recipient, sampleCost,
petCategory, salesChannel, status, notifiedAt, createdAt, updatedAt
```

| 字段 | 说明 |
|---|---|
| `type` | `寄样合作` / `不寄样合作` / `直播定向`。**判断走 `rules.needsSample(type)`，不要散着比字符串** |
| `recipient` | **这次实际用的**收件信息 |
| `sampleCost` | 整条合作的寄样费用 |
| `status` | `待寄样` / `进行中` / `已寄样` / `已完成` / `已终止` |
| `notifiedAt` | 告知达人的时间，null 表示还没告知 |
| `salesChannel` | 带货方式（短视频 / 直播） |

**收件信息故意冗余。** `creators.defaultRecipient` 是达人当前的地址，
`collaborations.recipient` 是这次发货用的。达人改地址**不应该**
追溯改掉历史合作的发货记录 —— 那是已经发生的事实。

**「进行中」是不寄样合作的起点。** 它没有寄样这一步，落成「待寄样」的话
表里会一直挂着一个永远不会被寄的东西 —— 筛选的人以为有活要干，
点进去才发现根本不需要寄。

**状态由动作驱动。** 只有「已终止」「已完成」允许手动置，
其余全部由动作推导：回填快递单号 → 自动变「已寄样」。
界面上没有状态下拉框，`ui.test.js` 有条测试专门守着这个 ——
断言的是「状态接口的调用点只传『已终止』」，而不是搜字符串
（代码里有 `['待寄样','已寄样'].includes(...)` 这样的合法过滤，按字面量禁会误伤）。

### `collab_items` —— 产品行

```
id, collaborationId, productId, productName, quantity
```

`productName` 冗余存了一份。产品改名后，历史合作里应该显示当时的名字。

### `collab_accounts` —— 履约项（账号级）

```
id, collaborationId, accountId, expectVideo, filmingProgress,
shareToken, videoUrl, publishedAt, deliveryStatus, planId
```

**这张表是「这次合作里，这个账号要做什么、做到哪了」。**

| 字段 | 说明 |
|---|---|
| `expectVideo` | 这个号是否要出片 |
| `filmingProgress` | `待拍摄` / `已催拍` / `已发布` / `本次不出片` |
| `shareToken` | 抖音分享口令。**逐字节保存，改一个字符就可能失效** |
| `videoUrl` | 视频链接 |
| `deliveryStatus`, `planId` | 投流预留，本期不启用 |

**拍摄进度在履约项上，不在合作上** —— 一个达人的两个号可以一个已发布、
一个还没拍。这一层是矩阵号场景存在的全部理由。

> 飞书的系统表一行是「一条合作 × 一款产品」，压平掉了账号这一层，
> 所以同步时才有「多账号只能拼接成一格」的问题。见 `飞书同步方案-v2.md`。

### `packages` —— 包裹

```
id, collaborationId, carrier, trackingNo, shippedAt, source, shotId, createdAt
```

`source` 记录来源：`manual` 手工填 / `screenshot` 截图识别。
`shotId` 指向 `data/shots/` 下的那张原图 —— 单号对不上时，
只有原图能说明是模型看错了还是仓库本来就发错了。

**图不在库里。** 一张 base64 后 0.5～3 MB，而启动备份保留 7 份 `naimeng.db`，
图片进库就是 7 倍体积。所以只存 id，图落文件，按数量上限单独清理。

**同单号重复回填是幂等的** —— 仓库发的截图里同一个单号出现两次，
不会建出两个包裹。

一条合作可以有多个包裹（分批发、补发）。

## 四、支撑表

| 表 | 一行代表 | 说明 |
|---|---|---|
| `products` | 一个产品 | `name, petCategory, spec, active`。停用用 `active` 而不是删除 —— 历史合作还引用着它 |
| `users` | 一个成员 | `id, name, role, phone`（角色：`business` / `operations` / `warehouse`）。**姓名唯一** —— 登录时的成员名单是按姓名给人选的，重名就分不清谁是谁。改资料走 `updateUser(id, ...)`，按 id 不按姓名 |
| `jobs` | 一个识别任务 | `rawText` 或 `imageBase64` → `result`。异步队列，前端轮询 |
| `intake_logs` | 一次建档 | 原文 + 模型抽取 + 人工修正的 `diff` |
| `drafts` | 一份草稿 | 未提交的录入 |
| `other_accounts` | 非抖音账号 | 视频号 / 快手等，已建表未启用 |

### `intake_logs` 值得单独说

```
id, createdAt, creatorId, collaborationId, rawText, extracted,
model, mode, promptVersion, diff, confirmedBy, confirmedByName,
confirmedAt, elapsedMs
```

它记的是**模型抽出来什么、人改成了什么**。

这是将来调优提示词唯一的真实语料 —— 每一条 `diff` 都是一次
「模型在这里判断错了」的标注，而且是免费的、在正常使用中自然积累的。

**不要清理这张表。** 它会长大，但它是这个系统里最有价值的数据之一。

> 和 `op_logs` / `err_logs` 是三件事：这张是**语料**（模型抽出什么、人改成什么），
> `op_logs` 是**审计**（谁做了什么），`err_logs` 是**排查**（哪里坏了）。
> 合并任何两个都会让第三个用途变难。

## 五、基础设施表

| 表 | 状态 | 说明 |
|---|---|---|
| `sessions` | 空 | 会话现在是 HMAC 签名 cookie，过期时间写在签名载荷里，服务端自校验。这张表留着是为了将来需要「主动踢人」时用 |
| `identities` | 空 | 外部身份绑定。为飞书登录留的，后来决定用团队口令，没启用 |
| `op_logs` | — | 操作日志：谁在什么时候动了什么。**不含请求体**，不设上限（审计线索剪掉就失去意义） |
| `err_logs` | — | 错误日志：`source` / `message` / `stack`，写入前脱敏，只留最近 1000 条 |
| `outbox` | — | 飞书推送队列。业务动作只入队就返回，`entityId` 是**合作 id** |
| `sync_links` | — | rowKey ↔ 飞书 record_id。`entityId` 是 **`合作ID#产品行ID`** |
| `meta` | 3 行 | `schemaVersion` 等 |

> **两张表的 `entityId` 含义不同，别弄混。** 入队的单位是「一条合作」
> （改了什么、有几款产品，入队时还不知道也不该知道）；
> 而飞书里一行是「一条合作 × 一款产品」，所以映射表按 rowKey 存。
> 展开发生在推送时 —— 入队时算出来会过期。
>
> 同步状态（未同步 / 待同步 / 已同步 / 同步失败）由这两张表**推导**，
> 不在合作表上存一份：存一份就要在每个改状态的地方记得更新它，
> 迟早漏一处，而漏掉的表现是「界面说已同步、飞书里其实没有」。

### 出站队列为什么必须存在

**同步失败绝不能影响商务干活。** 业务动作往 `outbox` 塞一条记录就返回，
真正的推送在后台做，失败按 1 分钟起步、最长 30 分钟的退避重试。

飞书挂了、断网了、令牌过期了、列名被人改了 —— 商务照样能建档、能回填快递。

入队动作 `markDirty()` 放在 **db 层**而不是路由层。放路由层意味着
每加一个接口都要记得调一次，迟早漏掉一处。

## 六、不在数据库里的

### `data/shots/` —— 发货截图存档

一张 base64 之后 0.5～3 MB。启动时会把整个 `naimeng.db` 备份并保留 7 份，
**图片进库等于这些体积乘以 7** —— 而备份的价值在达人资料和合作记录，
不在几个月前的一张快递截图。

所以图落文件，库里只存 `shotId`，超过 1000 张从最老的删起
（文件名带时间戳，排序就是时间序）。

原图**走接口不放静态目录** —— 静态目录意味着同网段谁都能按 id 猜着看。
id 用白名单校验（必须长成 `sh-xxx-yyy`），不是「过滤掉 `..`」：
过滤是黑名单思路，而且对不含 `..` 的名字完全放行，目录里任何文件都能被读出去。

### `data/settings.json`

```
auth.passphrase       团队口令的 scrypt 哈希（不存明文）
model / vision        文本模型、视觉模型配置（含 API Key）
feishu                飞书同步配置（含 App Secret、列映射）
followUp              回访节奏
notifyTemplate        告知达人的文案模板
```

> **这里曾经有一个 `user` 键**，存「当前用户」的姓名角色电话。
> 它是全局的、谁保存谁覆盖：商务甲打开设置页看到的是商务乙最后存的资料，
> 一点保存还会按姓名去 users 表匹配，改到商务乙的记录上。
> 现在身份只由会话决定，这个键在加载时被直接丢掉 ——
> 留在文件里迟早有人再读它一次。

**为什么不进数据库**：它整体读写、从不查询，进表没有收益；
出问题时能直接打开看，是排查时的优势。

代价是它不在 SQLite 的事务里 —— 但设置的写入本来就是单点、低频的。

> `data/` 整个目录在 `.gitignore` 里。里面有 API Key、口令哈希、
> 会话签名密钥，以及达人的真实姓名手机号地址。**永远不要提交。**

## 七、ID 规则

统一 `前缀-五位序号`：

```
cr-00042   creators          cb-00042   collaborations
ac-00042   accounts          ci-00042   collab_items
ca-00042   collab_accounts   pk-00042   packages
pd-00042   products          u-00042    users
jb-00042   jobs              lg-00042   intake_logs
df-00042   drafts            oa-00042   other_accounts
ob-00042   outbox
```

序号从 `meta` 表取，全局递增不复用。

**可读性是有意为之** —— 排查时一眼能看出「这个 id 是哪张表的」，
不用回去查。飞书同步的系统ID 也直接用它。

## 八、备份与迁移

**备份**：启动时自动备份到 `data/backups/`，保留最近 7 份。
但那些副本和数据库在同一块硬盘上，硬盘坏了一起没 —— 必须往外拷一份，
见 `DEPLOY-macmini.md` 第 9 节。

**迁移**：`meta.schemaVersion` 当前是 2。v1 → v2 的迁移
（达人/合作分离）在 `migrateV1toV2()` 里，包在一个事务中。

> 迁移代码有过两次同类事故：判断版本时写了 `raw.schemaVersion || 2`，
> 老数据里没有这个字段 → 取到 2 → **迁移被静默跳过**，没有任何报错。
> 正确的是 `|| 1`。写新迁移时注意这个方向：**默认值要取旧版本，不是新版本。**
