# 飞书同步方案 v2：系统表 + 关联引用

> **状态：代码已实现。** 系统表列定义在 `lib/feishu-schema.js`，
> 推送逻辑在 `lib/sync.js`，回归在 `tests/feishu.test.js`（43 条）。
> 剩下的是飞书那边的操作：建表、建关联列、配自动化。

> v1（直接往团队表推）已废弃，见 `飞书同步映射设计-v1.md` 顶部说明。
> 换方案不是因为 v1 做不出来，是因为 v1 要用代码去迁就一张**不归我们管**的表 ——
> 那种依赖平时看不出问题，改表的人一动就断，而且断了没人知道。

## 一、结构

在同一个多维表格里**新建一张「系统表」**，只有程序写它。
团队现用的那张表（`tbl2zfl51fVdGq5n` 达人寄样信息）保持原样，
通过**关联 + 查找引用**去引系统表的值。

```
  ┌────────────────────┐        ┌──────────────────────────────┐
  │   系统表（新建）    │        │  团队表 tbl2zfl51fVdGq5n     │
  │                    │◄──关联─┤                              │
  │  只有程序写         │        │  关联列 → 系统表             │
  │  28 列，类型全可控   │        │  查找引用：抖音昵称           │
  │  一行 = 合作×产品行 │        │  查找引用：快递单号           │
  │                    │        │  查找引用：拍摄进度  …        │
  └────────────────────┘        │                              │
                                │  达人等级    ← 人工，不碰      │
                                │  是否发投    ← 人工，不碰      │
                                │  物流状态    ← 自动化，不碰    │
                                └──────────────────────────────┘
```

**边界：系统表归程序，团队表归人。我们不写团队表一个字。**

### 为什么用引用而不是自动化复制值

自动化是触发式的：系统表变一次 → 跑一次 → 把值写过去。三个问题：

1. **消耗配额。** 我们的推送是全量覆盖式的 update，值没变也可能触发。
2. **失败无声。** 自动化没跑成，两张表就不一致，而且没有任何提示。
3. **跨表 upsert 是难点。** 要把系统表的一行对应到团队表的一行去更新，
   依赖「查找记录」能力 —— 这一项是否可用、在哪个套餐可用，**尚未验证**。

查找引用列是**实时跟随**的：系统表改了，引用列立刻是新值。
不跑流程、不消耗配额、不会失败。

**自动化只干一件事**：系统表新增记录时，在团队表建一行并建立关联。
一条记录一辈子只跑一次。

> 团队表里已经有「重复检测」（双向关联）和「父记录 2/3」（关联），
> 说明这套机制团队已经在用，不是新概念。

## 二、粒度：一行 = 一条合作 × 一款产品

和团队表的「一次寄样 = 一款产品」对齐，关联就是 1:1。

如果系统表按「一条合作」而团队表按「一款产品」，自动化要做 1→N 展开
—— 那是它最不擅长的事。

**行标识**：`系统ID` 列存 `合作ID#产品行ID`，例如 `cb-00042#ci-00107`。

用产品行的 `id` 而不是数组下标 —— 下标会因增删产品整体错位，
把 A 产品的数据覆盖到 B 那一行。这种 bug 表现为「数字不对」，
很难联想到是键的问题。

**多账号**：一条合作挂多个抖音号时，账号相关的列用「、」拼接。
当前库里 4 条合作全是单账号，这个代价暂时是零。真出现矩阵号且
需要分别追踪出片时，再考虑把粒度加细到 `合作 × 账号 × 产品`。
**现在不加细** —— 会让单账号（绝大多数）的情形凭空多一层复杂度。

## 三、系统表的 28 列

定义在 `lib/feishu-schema.js`，那是唯一真相来源，改列改那里。

**类型只用四种**：多行文本(1) / 数字(2) / 日期(5) / 复选框(7)。

刻意不用单选和多选 —— 它们要求写入的值必须已存在于选项里，
否则报 1254043。每上一个新品就得记得去飞书加选项，忘了就同步失败。
这种「平时没事、关键时刻炸」的依赖不值得为了好看引入。
团队表想要彩色标签，在它自己那边用单选列 + 自动化转换。

### 「寄样费用只写第一行」

`sampleCost` 是**整条合作**的费用，而我们按产品拆成了多行。
每行都写，飞书的求和统计会翻倍。

只写第一行不完美 —— 看第二行的人会以为没花钱。但相比一个悄悄虚高的
合计数，「有一格是空的」是更容易被发现、也更容易问清楚的问题。

单产品时不存在这个问题，而当前全部是单产品。

### 「收件信息」这一列含真实 PII

姓名 + 手机号 + 地址拼成一段。**谁能看这张表就等于谁能看这些**，
和系统里的权限是两套，需要各自确认。

## 四、怎么建

### 1. 在飞书里新建一张空表

多维表格左下角「+」→ 新建数据表，名字建议 `系统同步`。
不要用现成的表。

### 2. 用脚本把列建好

```bash
cd ~/apps/naimeng-intake
node tools/feishu-inspect.js                        # 找到新表的 table_id
node tools/feishu-scaffold.js <新表的table_id>       # 预演，只打印计划
node tools/feishu-scaffold.js <新表的table_id> --apply
```

**默认是预演**，不加 `--apply` 什么都不做。

脚本只新建缺的列，已存在的一律不碰（不改名、不改类型、不删除），
可以反复跑。如果发现表里有 3 列以上不属于系统表定义的列，
会**拒绝执行**并提示「看着像团队正在用的表」—— 防的是手滑贴错 table_id。

飞书新建数据表会自带几列默认字段（文本、单选、日期之类），
删掉除索引列以外的默认列，再把索引列改名成「系统ID」，
或者直接留着 —— 它们不影响同步，只是看着乱。

### 3. 在系统里指向新表

设置 → 飞书同步 → 数据表选成新表 → 映射按同名列自动对上，核对一遍。

### 4. 在团队表里建关联和引用

1. 团队表加一列，类型选**关联**，关联到系统表
2. 再加若干列，类型选**查找引用**，引用刚才那个关联列 + 系统表的某一列
3. 需要哪些字段就引哪些，不需要的不引

### 5. 建自动化：新增时自动关联

- 触发：系统表**添加新记录时**
- 操作：在团队表**新增一条记录**，关联列填触发记录

**这一步是整个方案的地基，务必先手工验证一次**：
在团队表手工建一行、手工关联一条系统表记录，确认查找引用列能显示出值。
显示不出来的话，说明关联/引用这条路走不通，得退回自动化复制值的方案。

## 五、这个方案解决掉的 v1 遗留问题

| v1 的问题 | v2 |
|---|---|
| 多选列要数组，值还得在选项里 | 系统表的列由我们建，全用可控类型 |
| 会覆盖物流那五列 | 我们根本不碰团队表 |
| 删产品行要删飞书孤儿行 | 只删系统表自己的行 |
| 历史行没有系统ID，首次推送会重复 | 系统表是新建的，从零开始 |
| 「归属人」「寄样产品」是多选，推送必失败 | 不再是阻塞项 |

`coerce()` 缺多选（type 4）**仍然是个真 bug**，只是不再阻塞上线。
将来有人把系统表某列改成多选就会踩到，该修还是要修。

## 六、已知的边界

**删除不传播。** 系统里删掉一条合作或一款产品，系统表那行会删，
但团队表那行只是断了关联，**不会自动消失**。得让团队知道，
不然会出现「系统里没了，飞书里还挂着」。

可以在团队表加一个「关联为空」的视图筛选，定期清理孤儿行。

**引用列是只读的。** 团队表里那些查找引用列改不了 —— 这是对的，
数据的所有权在系统这边。要改就去系统里改。

**自动化配额。** 按套餐限额。用关联方案的话一条记录只跑一次，
压力很小；退回复制值方案的话每次更新都跑，量大时要算。

**这仍然是单向的。** 团队表里人工填的列（达人等级、是否发投、备注）
不会回到系统里。要回流是另一个课题，复杂度高好几倍，现在不做。

## 七、代码侧已完成的部分

1. ✅ **推送单位是「合作 × 产品行」**。`buildFields` 之上有一层展开，
   `sync_links.entityId` 存 rowKey。出站队列仍按合作入队（`markDirty` 不动），
   展开发生在推送时 —— 「有几行」随产品行增删变化，入队时算出来会过期。

2. ✅ **SOURCE_FIELDS 由 `feishu-schema.js` 派生**，`get()` 签名是 `(cb, item)`。
   模块加载时校验每一列都有取值函数，缺了直接抛 ——
   之前两处各维护一份，丢了四个字段且毫无报错。

3. ✅ **删孤儿行**。只删 `sync_links` 里记着的 record_id，手工加的行不碰；
   放在最后做，先写该有的再删多余的。

4. ✅ **映射按同名自动匹配**，并提示「已自动匹配 N 项，核对后记得保存」。

5. ✅ **同步状态可见**：记录表一列 + 详情里的失败原因和手动重推。

6. ⬜ `coerce()` 仍未处理多选（type 4）。系统表不用多选，所以不阻塞 ——
   但将来有人把某列改成多选就会踩到，该修还是要修。
