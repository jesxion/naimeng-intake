# 飞书插件可达性验证

**这是一次探路，不是功能。** 目的只有一个：搞清楚飞书插件能不能连上
局域网里的这套系统。它决定后面所有设计——猜错方向能浪费好几天。

---

## 为什么必须先验证

飞书插件是加载到飞书客户端里的一个前端页面。而系统跑在
**局域网 Mac mini 的 `http://192.168.x.x:5173`** 上。中间隔着四道，
**每道的解法完全不同**：

| # | 问题 | 失败了意味着什么 |
|---|---|---|
| 1 | 页面能不能被飞书加载 | 托管要求（HTTPS？备案域名？审核？） |
| 2 | 能不能连上局域网地址 | 混合内容拦截 / 网络不通 |
| 3 | 跨源放行了吗 | 服务端没发 CORS 头 |
| 4 | 带凭据能不能认出身份 | 鉴权方式不对 |

不拆开的话，插件那边只会看到一个笼统的失败，而那个失败可能是这四种里的任何一种。

## 一个死结，先说清楚

**跨源用不了现在的会话 cookie。** 这不是没配好，是绕不开的：

- 现在是 `SameSite=Lax` → 跨站请求**根本不带**
- 改成 `SameSite=None` → 浏览器**强制要求** `Secure`
- `Secure` → 明文 http 上浏览器**不回传**

只要系统还在局域网 http 上，这三条就锁死。所以跨源客户端走
`Authorization: Bearer` 令牌——它不受 SameSite 约束。

**副作用是好的**：令牌不是环境权限（不会自动带上），
所以跨源那条路的 CSRF 面是零。这也是 CORS **刻意不开
`Allow-Credentials`** 的原因。

---

## 怎么跑

> ### ⚠️ 必须在飞书插件里打开这个页面
>
> **直接用浏览器打开 `http://192.168.x.x:5173/probe.html` 测不出任何东西。**
> 那时候页面和系统同源、cookie 正常带上、没有 CORS —— 四步会全绿，
> 但那是系统本来就成立的情形，和插件能不能用毫无关系。
>
> 第一次验证就是这么废掉的：报告显示「四步全过」，
> 而实际上源是 `http://192.168.1.18:5173`（系统自己的地址），
> 匿名请求却认出了身份（说明带了同源 cookie）。
>
> 探针第 1 步会检查是不是在插件容器里。判据见下面「第 1 步判据」一节 ——
> 它改错过两次，值得单独看一眼。

### 最省事的一种：先试把系统地址直接注册成插件

**如果飞书愿意直接加载 `http://192.168.x.x:5173/probe.html` 作为插件**，
那 CORS 和 SameSite 两个问题当场消失 —— 页面和系统同源。

先试这个。成了就不用往下看。**但要在飞书里打开，不是在浏览器里。**

### 完整四步

1. 系统里签一个令牌：设置 → 外部接入 → 填用途 → 签发。
   **明文只显示这一次**，立刻复制。
2. 把 `public/probe.html` 放到飞书能加载的地方（或者直接用系统自己的
   `/probe.html`）。
3. 打开它，填系统地址和令牌，点「开始检测」。
4. 点「复制结果」，把报告贴出来。

探针会在每一步失败时说清**那意味着什么**，不用自己猜。

### 第 3 步要是提示源没放行

设置 → 外部接入 → 把探针页显示的那个源加进白名单。
只填协议+域名+端口，路径会被自动截掉。

---

## 结果怎么读

| 卡在哪 | 结论 |
|---|---|
| 第 1 步（页面加载不出来） | 飞书对托管有要求。查它的插件文档，或者先把插件传到它的托管上 |
| 第 2 步报**混合内容** | 系统必须上 HTTPS。`mkcert` 做本地 CA 可行，代价是每台机器装根证书 |
| 第 2 步报**连不上** | 网络问题。同网段吗？防火墙放行 node 了吗？浏览器直接打开这个地址出得来吗 |
| 第 3 步说源没放行 | 加白名单就行，不是障碍 |
| 第 4 步认不出身份 | 令牌错了/过期了/被吊销了 |
| **四步全过** | 插件方案成立，可以往下做 |

---

## 这次顺带做了什么

探针只是壳。真正加上的是**外部客户端接入能力**，
它无论插件成不成都用得着（MCP 适配也走这条）：

### `Authorization: Bearer` 令牌

- 和会话 cookie **共用一个身份入口** `userOf(req)`——
  「身份只有一个入口」那条规则没破
- payload 里带 `k` 区分类型：**web 会话和 API 令牌不能互换**。
  能互换的话，一个泄漏的长期令牌就等于一个永久 cookie
- payload 里带 token id，`settings.apiTokens` 存清单。
  **从清单里删掉就立刻失效**——纯 HMAC 无状态方案吊销不了单个令牌，
  而「发出去的凭据收不回来」是不能接受的
- **明文只在签发那一次返回**，库里只存 id 和使用记录。
  存明文等于把长期凭据落在 `settings.json` 里，而那个文件出问题时人会直接打开看

### CORS

- **白名单，默认为空**（= 跨源全关）
- **不开 `Allow-Credentials`**——跨源只认令牌不认 cookie
- 回显 Origin 时带 `Vary: Origin`，否则中间层可能把 A 站的响应缓存给 B 站
- **预检在鉴权之前答复**：浏览器发 OPTIONS 时不带 `Authorization`，
  挡在 401 里的话真正的请求根本发不出去，而现象是「CORS 报错」，
  完全看不出是鉴权顺序的问题
- 保存时把 URL 归一成纯 origin。带路径的值会在比对时永远不匹配，
  现象像「白名单配了没生效」

### `GET /api/ping`

匿名可访问，回 `{ ok, service, time, you, corsAllowed }`。

它的存在意义是**让「网络通不通」和「凭据对不对」变成两个能分开回答的问题**。
因此必须匿名，也因此必须什么都不带——有测试守着它不泄漏业务数据。

## 第 1 步判据：错过两次

这一步的任务是回答「这到底是不是跑在飞书插件里」。它错了两次，
**方向相反，病因相同**。

### 第一次：假通过

第一次验证报告显示四步全过，但那是在普通浏览器里直接打开系统页面跑的。
当时第 1 步写的是「你现在能看到这个页面，这一步就过了」——
那句话在普通浏览器里也成立，于是给了一个假的通过，
后面三步全部基于一个错误的前提。

### 第二次：假失败

改成硬判据：`bitable SDK 已注入 或 (在 iframe 里 且 UA 含飞书标识)`。
结果在**真的插件面板里**判了失败。两个假设都不成立：

- `@lark-base-open/js-sdk` 是 **npm 包，要页面自己 import**，容器不会注入。
  「未注入」根本不能说明什么
- UA 里的 `Lark` 标识只有**飞书客户端**才有。在浏览器里打开飞书网页版时，
  iframe 继承的是浏览器自己的 UA

### 现在的做法

不再用单一信号下硬结论。摆出四条证据，按可靠性排：

| 证据 | 可靠性 |
|---|---|
| `location.ancestorOrigins` 里有飞书域名 | 浏览器给的，页面伪造不了 |
| `document.referrer` 指向飞书 | 可能被 referrer policy 削成 origin，够用 |
| UA 含 `Lark`/`Feishu` | 只在飞书客户端里成立 |
| `window.bitable` 存在 | 只说明页面自己引了 SDK，**不是容器证据** |

判定：

- **顶层窗口**（不在 iframe 里）→ 判「不是」。插件一定是嵌进去的，这条一票否决
- 在 iframe 里 + 上面任意一条指向飞书 → 判「是」
- 在 iframe 里但一条都拿不到 → 判「**说不准**」，继续往下跑，把结论留给人

第三格是关键。判「不是」就回到第二次的假失败，判「是」就回到第一次的假通过。
**这一格的正确答案是不下结论。**

### 教训

两次都是同一句话的两种表现：

> **一个在错误情况下也会通过的检查，等于没有检查；
> 一个在正确情况下会失败的检查，同样等于没有检查。**

前半句在这个项目里踩过五次。后半句这是第一次——它更隐蔽，因为
「测出来是红的」看上去像是在干活。

判据现在被 `tests/probe.test.js` 守着：把它抠出源码直接跑，
四种环境各一条用例。五项变异全部被抓到：

```
退回第二版判据（只认 SDK/UA）  → 4 红
不看 ancestorOrigins           → 2 红
拿不到痕迹时判「不是」          → 1 红
顶层窗口也放行                 → 1 红
域名正则不匹配裸域名            → 2 红
```

最后一条是写测试时顺带抓到的真 bug：正则写成 `(^|\.)feishu\.cn`，
匹配得上 `example.feishu.cn` 但匹配不上 `https://feishu.cn`（前面是斜杠）。
而 `ancestorOrigins` 给的恰恰是裸源。**只测一种输入的话这个洞会留着。**

## 验证记录

九项变异全部被抓到：

```
开了 Allow-Credentials          → 1 红
白名单不校验，谁都放行           → 2 红
回显 Origin 却不带 Vary          → 1 红
不查清单（吊销失效）             → 1 红
不归一 origin                    → 1 红
不校验令牌类型                   → 2 红（第一轮 0 红，见下）
API 令牌能当 cookie 用           → 2 红（第一轮 0 红，见下）
```

后两条第一轮都没红——它们是「凭据类型混用」这一类，
而 HTTP 层**造不出**「签名合法但类型不对」的串。补了三条直接调 `auth`
模块的用例才抓到（测试和被测服务共用 `NAIMENG_DATA_DIR`，所以密钥相同）。

> 教训和之前几次一样：**能从外部证伪的就从外部测；外部证伪不了的，
> 就得往下钻一层。** 只在 HTTP 层测，这两个洞会一直留着。

端到端也实跑过一遍（起真服务 + curl），六条性质逐一确认：
匿名探针可达、Bearer 认出身份、Bearer 能读业务数据、无令牌 401、
白名单为空时跨源被拒、吊销后立刻 401。
