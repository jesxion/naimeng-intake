### B. 真正的鸡肋：一件事两种做法

**「标记已告知」在工作台是两步，在合作详情里是一步。**

- 工作台待办卡片：「复制文案」和「标记已告知」是**两个按钮**（`app.js:500,505`）
- 合作详情：复制完整物流信息**即视为已告知**（上一批改的）

同一个动作，两个界面两种语义。用工作台的人会觉得详情页「怎么没问我就标了」，
用详情的人会觉得工作台「怎么还要多点一下」。

README 里这两处也互相矛盾：
- 第 140 行「复制文案和标记已告知**分两步**，避免复制了忘了发」
- 第 218 行「复制完整物流信息即视为已告知」

**两句都是真的**，只是描述不同界面 —— 而这正说明设计本身分叉了。

> 建议统一成「复制即标记」，并在工作台去掉那个独立按钮。
> 理由和上次一样：复制完再点一下「我复制了」，是让人做一件系统已经知道的事。
> 反对意见也成立（复制了不一定发出去），但**不该由界面决定用哪种**。

### C. 抽取了、存了，但界面上永远看不见

**其他平台账号（视频号 / 快手 / 小红书 / 微信）。**

- 提示词专门要求抽取（`agent.js:42,59`），还特别强调不许混进抖音号
- `rules.js` 归一化、`sanitizeForStore` 保留、`db.addAccounts` 入库
- 前端 **零渲染**：`grep -c "视频号\|快手" public/app.js` → `0`

也就是说这条链路从头到尾都在工作，唯独最后一步没有出口。
商务粘进来的视频号进了库，但谁也看不到，等于没有。

> 要么在达人档案卡片里加一行显示出来（几行代码），
> 要么把提示词里那两条删掉、停止抽取。
> **现在这样是最差的**：花了 token、占了库、还给了「系统记着呢」的错觉。

### D. 预留但没有数据来源的字段

| 字段 | 状态 |
|---|---|
| `collab_accounts.deliveryStatus` / `planId` | 投流预留，前端零引用 |
| `creators.channel` / `remark` | 只在 db.js 写入，界面上不显示也不可编辑 |
| `collaborations.salesChannel` | 详情里只读显示一行，但**没有任何地方能填它** |
| `sessions` / `identities` 两张空表 | 文档已说明是为将来留的 |
| `other_accounts` 表 | 同 C |

前三个是同一类问题：**有字段、没入口**。

`salesChannel` 尤其怪：详情页会显示「带货方式」，但录入界面没有这一项，
模型也不一定抽得到 —— 所以它多半永远是空的，那一行等于永远不显示。

> `deliveryStatus`/`planId`/`sessions`/`identities` 留着没成本（几个字节），
> 而且文档写清了为什么留。**这几个不算债。**
>
> `channel` / `remark` / `salesChannel` 该做个了断：要么给入口，要么删。

### E. 没有前端调用方的接口

`POST /api/creators/:id/accounts` —— 界面上没有「给已有达人补充账号」的入口。
`grep` 只在日志的动作名映射表里出现。

`GET /api/creators` 和 `GET /api/creators/:id` 现在只有测试在用 ——
上一批删掉 `openCreator` 之后，前端不再有任何「达人视角」。

> 这是个**设计缺口**而不是冗余：达人是这个系统的一等公民（归属挂在它上面、
> 合作码复用靠它），但界面上只能从合作进去看。
> 「这个达人一共合作过几次」现在没地方看。

## 三、可展望的功能

按「现在就能做 / 有前提 / 想清楚再说」分。真话在括号里。

### 现在就能做

**1. 达人视角（补上面 E 的缺口）**

一个达人页：所有账号、历史合作、总寄样费用、出片率。
数据全都有，只差一个界面。**这是投入产出比最高的一个。**

**2. 分页**

几百条合作后单次响应会到几 MB。现在 4 条看不出来，
半年后会突然变卡，而那时候人已经在依赖它了。

**3. 导出 CSV**

老板要数据时现在只能截图或者去飞书。一个导出按钮省掉很多来回。

**4. 飞书同步的收尾**

`coerce()` 的多选（type 4）还没做。系统表不用多选所以不阻塞，
但这是个**已知的坑**，写在文档里等着别人踩不太好。

### 有前提

**5. 物流轨迹**

现在「快递状态」只能说「待发货 / 已发货」，因为没有数据源。
接快递 100 / 快递鸟之类的 API 就能有真实轨迹。

前提：要 key、要花钱、要外网。而且**飞书那边已经有自动化在查物流** ——
先确认是不是重复建设，比直接开工重要。

**6. 投流三态**

字段早就留好了（`deliveryStatus` / `planId`）。
前提是**运营得进这个系统** —— 现在他们不进，
做出来就是一组永远没人填的字段，比没有更糟。

**7. 每人一套凭据**

现在共享口令。团队扩到十几人、或者需要「这条真的是他改的」这种级别的
证据时才有必要。6 个人同处一间办公室，现在做是提前优化。

### 想清楚再说

**8. 双向同步**

飞书那边人工填的列（达人等级、是否发投、备注）回流到系统。
复杂度是单向的好几倍：冲突、回环、谁赢。
**除非「运营只肯在飞书里干活」变成硬约束，否则不值得。**

**9. 提示词调优**

`intake_logs` 已经攒了一批「模型抽错了、人改成什么」的标注。
攒到一两百条时值得回头看：哪类字段错得最多，针对性改提示词或加 few-shot。

现在数据量还不够，**看了也是噪声**。

**10. HTTPS**

局域网明文。`mkcert` 做本地 CA 是可行的，代价是每台机器装一次根证书。
风险取决于办公室网络里有多少不受控设备 —— 这个我不知道，你知道。

### 已修

**「标记已告知」统一成一步。** 工作台的待办卡片从「复制文案」+「标记已告知」
两个按钮改成一个「复制物流并标记已告知」，和合作详情同一套语义。
有测试守着它们不再分叉。

**「带货方式」原来是个静默丢失的 bug，不是冗余。**
模型抽得到（提示词里有，还有正则兜底），但 `normalize` 不输出、
`sanitizeForStore` 不保留、路由不传 —— 于是 `salesChannel` 永远是空串，
详情里那一行永远不显示。和 `cooperation_type` 是**完全相同**的一处漏。
现在整条链路打通并有测试。

> 这类错误的共同形态：**中间任何一环断掉都不会报错**，
> 只表现为「那个字段永远是空的」。已经在 README 的分层原则里加了一条：
> 「抽了就要有出口」。

**其他平台账号有出口了。** `expandCollaboration` 把 `other_accounts`
带出来，达人档案卡片里显示成「其他平台 · N 个（仅存档）」。
之前模型一直在抽、库里一直在存、前端零渲染 —— 花了 token 又占了库，
还让人以为「系统记着呢」。

### 测试

351 → 360。五项变异全部被抓到：

```
带货方式又被丢掉          → 1 红
sanitize 不保留带货方式   → 1 红
其他平台账号不带出来      → 1 红
界面不显示其他平台账号    → 1 红（第一轮 0 红，见下）
工作台复制后不标记        → 1 红
```

「界面不显示其他平台账号」第一轮没红 —— 我的断言只搜了 `cb.otherAccounts`
在不在源码里，把守卫改成 `if (false)` 时代码还在，照样绿。
改成断言**条件本身**才抓到。

**这个坑在这个项目里踩过四次了**（`agentReady` 类型断言、
「复制后标记」、「无记录时说明」、这次）。规律很清楚：
**断言字符串存在 ≠ 断言行为发生**。
